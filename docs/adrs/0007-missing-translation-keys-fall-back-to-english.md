# ADR-0007: Missing translation keys fall back to English and warn

- **Status:** Accepted
- **Date:** 2026-10-26
- **Scope:** the `t()`/`tp()` lookup path in the i18n engine
- **Code:** `src/lib/i18n.ts` (`REFERENCE_LANG`, `DEFAULT_LANG`, the `raw === undefined`
  branch of `t`)
- **Related:** ADR-0006 (the engine), ADR-0008 (`DEFAULT_LANG`, which is a separate
  constant), ADR-0013 and ADR-0015 (dictionaries are generated and interim, so gaps
  are expected)

## Context

Three dictionaries must stay in step with a key set that grows every time a component is
touched, and two of the three are generated by machine (ADR-0013) and known to be interim
(ADR-0015). Gaps therefore happen in two ways: a developer adds a call site and forgets the
non-EN dictionaries, and a generated dictionary simply has no entry for a key. The behaviour
when a lookup misses is a product decision, not an implementation detail: the user will see
either an English word, a raw key like `no_results_text`, or nothing at all.

## Decision

Absent key = reference language, with a console warning. In the engine:

```ts
const DEFAULT_LANG = 'en';
const REFERENCE_LANG = 'en';

let raw = templates[current].strings[key];
if (raw === undefined) {
  if (current !== REFERENCE_LANG) {
    console.warn(`i18n: key '${key}' missing in '${current}', falling back to '${REFERENCE_LANG}'`);
  }
  raw = templates[REFERENCE_LANG].strings[key] ?? key;
}
```

1. **`REFERENCE_LANG` is the language whose dictionary is the source of truth**, and it is a
   separate constant from `DEFAULT_LANG` even though both are `'en'` today. Fallback
   language and start-up language are different questions (ADR-0008 owns the second);
   splitting them lets either change without silently changing the other.
2. **The reference dictionary is always consulted**, so an entry missing in `en` is missing
   everywhere and returns the key itself as the last resort (`?? key`). That is the only
   path that can render something meaningless, and it means a typo is loud on screen.
3. **The warning is skipped when `current === REFERENCE_LANG`,** so the reference
   dictionary stays the quiet one: warnings mean "this language is behind EN", which is
   the actionable message.
4. **`console.warn`, not `console.error` or a throw.** The value is recoverable and the app
   is still correct-ish; the app already uses `console.error` for genuine failures
   (e.g. `Erro ao carregar exercises:` in `src/components/ExerciseList.tsx`).

## Alternatives considered

- **Throw on a missing key.** Rejected: a translation gap would break the screen the user is
  mid-interaction on, in an app whose dictionaries are deliberately incomplete while being
  iterated. Development signal is still wanted, which is what the warning gives.
- **Fall back to the raw key only (no reference language).** Rejected: it would render
  `tension_medium` to the user for every gap, which is worse than showing the English word
  and is a strict regression against the option actually chosen.
- **Fall back to Portuguese**, the language the app shipped in. Rejected: PT is not the
  reference dictionary, it is itself generated and folded-ASCII (ADR-0015), so a PT fallback
  would launder known-suspect text into EN and ES screens alike.
- **Fall back to any other available language** (walk `LANGUAGES`). Rejected: it makes the
  rendered language unpredictable and order-dependent, which is exactly what a reviewer
  auditing dictionaries cannot afford.
- **Silent fallback.** Rejected: silent fallback is how a whole generated dictionary can
  stay identical to English (ADR-0015's `es.ts`) without ever being noticed.
- **Return an empty string.** Rejected: an empty button or empty heading is a layout bug the
  user reports against us instead of a string we can see in a console.
- **Fail hard at build time (require all keys, enforce in types).** Not chosen: the key set
  is dynamic strings (ADR-0006), so the compiler cannot see it; the parity script in
  ADR-0006's Verification is the static equivalent, and runtime fallback covers the case
  that script was not run for.

## Consequences

- The app never shows `undefined` and never loses a UI label because of a gap; a gap degrades
  to one language (EN) that the reference dictionary is guaranteed to have.
- Partial translation is possible and intentional: an ES screen with EN fallback words will
  read mixed-language. That is now a signal to fix a dictionary, not a symptom to chase in the
  component.
- Missing keys are invisible to the typechecker but visible twice: once in the browser
  console (which is where ADR-0015's defect list came from, plus the parity script) and once
  as English inside a non-English UI.
- Because the last resort is the key itself, a key-name typo produces visible snake_case
  in all languages at once - easy to spot, and the only failure mode this decision can produce.
- `en.ts` must never be the one that lags. It is hand-authored (ADR-0013) and is the input to
  the generators, which is what keeps that ordering true.

## Verification

- Parity check (`/tmp/opencode/check-locales.mjs`): 63 keys in each dictionary, 63 used, zero
  missing in either direction - so in a clean tree no warning should ever fire.
- Grepping the built output for the warning text confirms the branch ships:
  `grep -n "REFERENCE_LANG\|falling back" src/lib/i18n.ts` returns lines 17-18 and 50-53.
- `npm run build` succeeds with the branch in place, i.e. the fallback is a runtime path, not
  a build-time one.
