# Software Requirements Specification

## 1. Overview and Purpose
The objective is to develop a full-stack web application to track and visualize musical practice progression, specifically targeting guitar technique evolution. This system replaces an existing manual tracking method based on spreadsheets, automating metrics calculation and providing a dynamic visual dashboard for performance analysis.

## 2. Core Entities and Data Structure
The business logic relies on two primary entities derived from the legacy spreadsheet model:

* **Exercise (Dimension):** The catalog of technical practices.
  * `Name`: Identifier of the exercise (e.g., "Spider Walk", "Punisher").
  * `Tab URL`: External link to the tablature (e.g., Songsterr link).
  * `Objective`: Biomechanical or technical focus (e.g., "Alternate Picking", "Motion economy").
  * `Max BPM`: The highest historical speed achieved.
  * `Last BPM`: The speed recorded in the most recent session.
  * `Dashboard Visibility`: A boolean flag determining if the exercise should be plotted on the main chart.
* **Practice Log (Fact/Event):** The transactional record of a daily practice session.
  * `Date`: Timestamp of the practice session.
  * `BPM`: The speed set on the metronome.
  * `Clicks per Beat`: The number of notes played per metronome click (e.g., 1, 2, 4, 6).
  * `Tension Level`: A subjective metric (e.g., integer scale from 1 to 3) indicating hand tension during execution, where 1 is completely relaxed and 3 is highly tense.

## 3. Functional Requirements

### 3.1 Exercise Management
* The system must allow users to create, read, update, and delete (CRUD) exercises in the catalog.
* Users must be able to toggle the "Dashboard Visibility" flag for each exercise to control the chart rendering.

### 3.2 Practice Logging
* Users must be able to submit a new practice log for any existing exercise, inputting the base BPM, clicks per beat, and hand tension level. The session's date is the day the log is written, not a field the user types (see Implementation notes).

### 3.3 Dashboard and Visualization
* The application must feature a primary dashboard displaying a tabular view of the exercise catalog.
* The dashboard must include a multi-series line chart mapping practice progression.
* Chart X-Axis: Time/Date of the practice sessions.
* Chart Y-Axis: `Real BPM`.
* Chart Data: Only exercises with the "Dashboard Visibility" flag set to true must be rendered on the chart.

## 4. Business Rules
* **Real BPM Calculation:** `Real BPM` is strictly the product of `Base BPM` multiplied by `Clicks per Beat`.
* **Record Updating:** When a new practice log is ingested, the system must evaluate the calculated `Real BPM`. If this value exceeds the `Max BPM` currently stored in the parent Exercise entity, the `Max BPM` must be overwritten with the new record.
* **Last Session Updating:** Every new practice log must overwrite the `Last BPM` field of its parent Exercise with the newly calculated `Real BPM`.

## 5. Acceptance Criteria
* A user can add a new exercise and submit daily practice logs against it, including their physical tension feedback.
* The multi-series line chart accurately reflects the historical `BPM` data points, matching the visual output of the legacy spreadsheet chart.
* The backend successfully calculates and updates the `Max BPM` and `Last BPM` asynchronously without requiring manual user input for these specific fields.

## 6. Implementation Notes (recorded during implementation, 2026-10-28)

These notes do not change the spec above; they state how the implementation reads it, so that a later reader can tell a deviation from an unmet requirement.

* **`Tension Level` storage:** the schema keeps an integer `1..3` with a CHECK, exactly the scale defined in requirement 3.1. The stored number is the level itself — no legacy scale, no normalization at read time — so the CHECK is the only guard. The wider `1..10` range this note used to record was removed on 2026-10-31, when the database was rebuilt locally: with no rows holding 4–10, tightening stopped discarding anything. The column's default is `2`, inside the range it checks. `src/lib/__tests__/tension.test.ts` pins the level-to-label/color mapping and greps the migration text for the range and the default, so schema and code cannot drift apart unnoticed.
* **`Max BPM` / `Last BPM`:** both are stored on the Exercise entity and written only by the backend — a Supabase trigger fired on every insert, update or delete of a practice log (scope widened by the one-record-per-day note below) — per acceptance criterion 3. Neither field is ever accepted as client input, and the UI reads the stored values rather than recomputing them.
* **`Real BPM`:** the product is spelled twice, once in the backend trigger that owns the two stored fields and once in `realBpm()` (`src/lib/bpm.ts`) used for display. `src/lib/__tests__/bpm.test.ts` pins the TS product numerically and greps the migration text for the same product, so the two cannot drift apart unnoticed.
* **Chart axis, legend and tooltip (2026-10-31):** acceptance criterion 2 asks for the legacy spreadsheet's visual output; the choices below are deliberate deviations requested during the implementation, not gaps in the data — the series themselves are unchanged (one per visible exercise, Y = `Real BPM`, X = the logged day). The X axis ticks one grid line per week instead of one per session; tick and tooltip labels follow the UI language rather than the chart adapter's default English; the tooltip shows the logged day with no clock time, since requirement 3.2 logs a date, not a moment; the year appears only when the plotted range spans more than one year; and the legend sits as a column on the right of the plot instead of above the axis, because the Y-axis title already occupies the left — on a plot measured narrower than 480px it moves above the axis, recorded below. `src/lib/chart.ts` holds the date rule and `src/lib/__tests__/chart.test.ts` pins it.
* **X-axis tick form (2026-11-02):** the ticks are the day and the month as digits — `09/14` where the locale leads with the month, `14/09` where it leads with the day — both fields padded, so the ticks line up in columns and no month name reaches the axis. The order is read from the locale rather than hardcoded per language. The tooltip still spells the day, and the year is appended on the same condition as above. Deliberate, decided 2026-11-02.
* **What a chart screen writes beside the plot (2026-11-02):** the quiet variant of `ProgressChart` — `compact`, off by default, turned on only by the session screen — drops the legend and the Y-axis title and halves the marks: the X axis steps two units instead of one, and the Y ladder is capped. The axis stays, because the window and the scale are still read off it; the tooltip already names the exercise, the logged day, the `Real BPM` and the tension for the point under the cursor, so the legend of a single label and the unit title beside the numbers repeat what hovering says. The guide lines keep their gray at a lower alpha rather than disappearing, since they mark the subdivisions `tickUnit` chose (`src/lib/period.ts`). The dashboard gets none of it: same unit, same step size, same ladder, same legend as recorded above. Deliberate, decided 2026-11-02; no other screen turns it on.
* **Tab link placement (2026-11-02):** requirement 2's field `Tab URL` is shown on the exercise's own screen (`src/components/SessionView.tsx`), where it is also stored and edited, not in the dashboard's catalog row. Acceptance criterion 2 asks the dashboard for a tabular view of the catalog, and the row is already the way to the screen that owns the link; a second copy in the row sat beside the exercise name, in the same brand red as the row's icon, and had to guard its own click against the row's navigation. The catalog therefore keeps title, `Max BPM`, `Last BPM` and the visibility toggle only. Deliberate, decided 2026-11-02; the dashboard shows no tab link — the exercise cards (`src/components/ExerciseList.tsx:146-159`) and the session screen do.
* **Catalog shape by width (2026-11-02):** acceptance criterion 2 asks the dashboard for a tabular view, so the table stays — header, four columns, the same rows — on `sm` and up. Below it the same rows are drawn stacked: name, then `Max BPM` / `Last BPM` as chips, visibility toggle at the right edge. Four columns inside 360px drag sideways and put a 24px control inside a row that navigates, so the list shape is the mobile deviation, not a missing feature; the eye is written once (`EyeCell`) because both shapes host it. Deliberate, decided 2026-11-02.
* **Chart layout by container width (2026-11-02):** a plot measured narrower than 480px puts the legend above the axis (`align: center`) instead of on the right, caps the X axis at 5 labels, and is 260px tall instead of 360px. The width is read from the container through a `ResizeObserver`, not from a media query, because a narrow column on a wide screen is narrow for the chart too — the session view's history card is one. A wide plot is unchanged: legend right, no X cap, 360px. Deliberate, decided 2026-11-02; `src/components/__tests__/chart-source.test.ts` pins both branches.
* **Period windows (2026-10-31):** the dashboard chart carries a `last month / last 3 months / last year / all data` control. It narrows the points plotted, not the records: `Max BPM` and `Last BPM` in the catalog stay the values the trigger stores, so criterion 3 is unaffected and nothing filters the fetch by date. The windows are durations rolling from the current day (30/90/365 days), so an idle stretch shows an empty window rather than re-anchoring at the last session; `all data` is the default, which keeps criterion 2 comparing the full log against the spreadsheet. The tick unit grows with the window drawn — weekly over a month or a quarter, monthly over a year — so the axis keeps its weekly-looking subdivisions at every period. `src/lib/period.ts` holds the arithmetic, `src/hooks/useChartPeriod.ts` the persisted choice, and `src/lib/__tests__/period.test.ts` pins both rules.
* **X axis ends at today (2026-11-07):** the scale is handed a domain instead of fitting itself to the series. A time scale sized by its own data puts the plot's right edge on the last day logged, so after an idle stretch the last session reads as the current day: the chart below stopped at 2026-11-04 while the day was 2026-11-07. The axis now runs from the oldest day actually plotted to the last instant of the current local day — or to the newest point, whichever is later, so nothing plotted ever falls outside the scale — which makes the empty stretch between the last point and the right edge the message, "nothing since then", rather than a misleading edge. The left edge deliberately stays on the oldest point: the period control filters the points plotted, it does not draw a frame the size of the window, and a window wider than the log would spend its width on axis that no day occupies. The right edge is the day the window is measured from, so the midnight refresh walks it forward without a reload, and it is the day's end rather than the instant because a session logged at 23:00 today has to fall inside the plot; the newest point wins over that edge when it is later, which is what a database clock running ahead of the browser's near midnight stamps. The tick unit and the conditional year are read from the days the axis covers — the points drawn plus today — so a log that stops in December prints the year once the axis runs into January; the anchor is the current instant, not the day's end, because 90 days measured to the end of a day read as 90.x and would switch the quarter's weekly lines to monthly ones. No label names a day that has nothing plotted on it, which is why the edge is that last instant rather than the midnight that opens the next day: the time scale walks its ticks in boundaries of its unit (weekly Sundays, month starts) and adds one at the axis maximum when the maximum falls exactly on a boundary, so an axis ending at Sunday's midnight printed `08/11` on Friday 2026-11-07, and a month end would print the next month's first day. Every unit boundary is a local midnight, so an edge one millisecond short of it can never be a boundary: the plot ends past its last label and the gap carries the reading. `axisMax`, `axisDomain` and `axisDays` in `src/lib/period.ts` hold the arithmetic, `src/lib/__tests__/period.test.ts` pins it, and `src/components/__tests__/chart-source.test.ts` pins that both branches of the chart hand the domain to the scale. Deliberate, decided 2026-11-07; the dashboard's BPM chart, the session screen's quiet chart and the song screen's percent chart all take it.
* **Session date (2026-11-01):** requirement 3.2 asked for the date as user input. It is instead the day the log is written: `practice_sessions.created_at` takes the schema default (`now()`), and `SessionView` sends only `exercise_id`, `tension_level`, `bpm`, `clicks_per_beat` and `notes` (`src/components/SessionView.tsx:142-147`), so the form carries no date field. One fact keeps one source — a typed date would be a second one — and the chart plots that day while the session history renders it in the UI language (`src/components/SessionView.tsx:526-534`). The edit path added by the one-record-per-day note below sends the same fields against the row's id and never touches `created_at`. Deliberate, decided 2026-11-01; nothing else writes a session date.
* **Environment (2026-11-01):** the old remote Supabase project is retired and will not be used again, so the schema edit made in place in `supabase/migrations/20261026230024_create_guitar_practice_tables.sql` — the tension range narrowed to `1..3` — needs no follow-up migration against the wider range it once applied. The local database, reset from zero by the CLI, is the environment the app runs against; the legacy log's rows live there and are not reproduced from the repository.
* **One record per day (2026-11-02):** requirement 3.2 says nothing about how many logs a day may hold; the implementation now keeps one per exercise per day. When the day already has a record the session form becomes its editor: it prefills from that row — today's row is read with `isSameLocalDay` over `created_at` (`src/lib/clock.ts`) — and the save is an UPDATE of the row instead of a second INSERT (`src/components/SessionView.tsx`). Past midnight the row stops being today's and the form returns to writing a new record, the boundary the day rollover already refreshes on; records of earlier days stay delete-only. The guard is the screen, not the schema: a session's day is the owner's local day and the database does not know that zone, so a unique index on a server-side date would misclassify rows logged near midnight, and a two-device race on the same day is the only case the index would catch in a tool with one owner. A record edited this way still moves the stored records: `sync_exercise_bpm_records` now recomputes `Max BPM` / `Last BPM` from the exercise's remaining sessions over INSERT, UPDATE and DELETE (`supabase/migrations/20261102213000_recalc_bpm_records_on_session_change.sql`), so criterion 3 holds through an edit and through deleting the day's row. Deliberate, decided 2026-11-02.
* **Accounts and ownership (2026-11-02):** the spec never names an account, so sign-in sits outside requirements 1–5 and the entities of requirement 2 are unchanged — same fields, same trigger-written `Max BPM` / `Last BPM`. What changed is who may reach them: `user_id` columns (`supabase/migrations/20261102150000_add_user_ownership.sql`) and RLS policies keyed on `auth.uid() = user_id` replace the `anon USING(true)` policies of the original schema, and `anon` is revoked from both tables, so the spec's "users" are now the account that holds the session. The owner of a new row is stamped by a `stamp_owner()` BEFORE INSERT trigger rather than sent by the client, so no write can claim another account's rows. One deliberate deviation: the log written before accounts existed carries no owner (`user_id` stays nullable), and `claim_legacy_rows()` moves those rows under the first account that signs in — first-come-first-served, which is the intent for a tool with one owner; a second account sees its own empty catalog. Email confirmation is off in `supabase/config.toml`, so a signup returns a session at once; the password floor is the config's `minimum_password_length = 6`, mirrored by `MIN_PASSWORD_LENGTH` in `src/lib/auth.ts`. `src/lib/__tests__/auth-schema.test.ts` greps the migration and config so neither drifts unnoticed.
* **Day check on the exercise cards (2026-11-02):** nothing in requirements 1–5 asks whether an exercise was practiced today, so the check leading a card's stat row (`src/components/ExerciseList.tsx`) is UI beyond the spec, and it stores nothing. The fact is read off the log: the exercise's newest `practice_sessions` row, asked against the owner's local day with `isSameLocalDay` (`src/lib/clock.ts`) — the same rule the one-record-per-day note above uses to find the row the form edits. Because a day holds one record per exercise, "the newest row falls on today" is the same fact as "a row exists today", so no `practiced_today` column and no trigger is added: deleting the day's record, or passing midnight, is what clears the tile. The list schedules the two boundaries the dashboard already schedules — local midnight, and the tab being looked at again — because a screen left open would otherwise go on marking yesterday. Two deliberate limits: the check is a status, not a control, since the card already opens the exercise on the same tap; and only the exercise list carries it, the dashboard's catalog keeping title, `Max BPM`, `Last BPM` and the visibility toggle as recorded above. Deliberate, decided 2026-11-02; `src/components/__tests__/exercise-list-source.test.ts` pins the day rule, the gated render and the refresh wiring.
* **Order of the exercise list (2026-11-02):** requirement 2 fixes what an exercise holds and requirement 3 what the log records, but neither names the order a catalog is shown in — the list had always been newest-created first. It now offers two orders, both read off the log: newest workout first, and most sessions first, through a two-button control beside the New-exercise button. Creation date is not an order a practice log is asked for, so it survives only as the last tie-break — the one among exercises that have never logged a row. Neither fact is a field of an exercise, and the REST API cannot order a parent row by its children (neither by how many rows they are nor by the newest timestamp), so the sort is done over the session rows the screen already reads for the chips and the day check (`src/lib/order.ts`) rather than by a new column or a second query. An exercise with no row counts as zero and lands last: never practiced is not the same as practiced long ago, so it sits behind every logged exercise whatever its creation date says. Two deliberate limits: the choice is a view preference kept in `localStorage` (`exercise_list_order`) and never written to the database — the only write this screen makes stays the visibility flag; and it applies to the exercise list alone, the dashboard's catalog staying newest-to-oldest as recorded above. Deliberate, decided 2026-11-02; `src/lib/__tests__/order.test.ts` pins the comparison and `src/components/__tests__/exercise-list-source.test.ts` the control and its persistence.
* **Songs as a separate entity (2026-11-03):** requirements 1–5 describe the exercise catalog and its daily log, and a song is neither: it is a fixed structure of N measures, each with the tempo the tablature sets there, practiced in blocks rather than at a metronome setting. Songs therefore get their own tables (`supabase/migrations/20261102230000_add_song_progress.sql` — `songs`, `song_measure_targets`, `song_progress_logs`), their own screens (`src/components/SongList.tsx`, `src/components/SongView.tsx`) and their own nav entry, and `exercises`/`practice_sessions` are untouched. A song never joins the dashboard's multi-series BPM chart, because its Y axis is a percentage of measures, not a tempo. Deliberate, decided 2026-11-02 (D1); nothing in requirements 1–5 covers songs, so this is an addition rather than a change.
* **Song percent (2026-11-03):** `percent numeric(5,2)` is stored on the song and written only by the `sync_song_percent*` triggers — insert, update and delete of a log, insert, update and delete of a measure target, and an update of `total_measures` — exactly the way `Max BPM` / `Last BPM` are owned above. The value is `100 * Σ over measures 1..total_measures of LEAST(1, MAX(bpm_clean of the logs covering that measure) / target.bpm) / total_measures`, spelled once in SQL (`song_percent()`) and once in TypeScript (`songPercent()` in `src/lib/songProgress.ts`) for display, with `src/lib/__tests__/songProgress.test.ts` pinning the arithmetic numerically and `src/lib/__tests__/song-schema.test.ts` grepping the migration for the same shape. Four deliberate deviations from the spreadsheet, decided 2026-11-02: the peak is what a measure keeps, so a slower log added after a faster one never lowers it (D2); `bpm_clean` ("Limpo") is the tempo that enters the math while `bpm_limit` ("Limite") is stored as information only (D4); every measure weighs 1 whatever its time signature, so a 7/8 measure counts like a 4/4 (D3); and overlapping blocks resolve per measure instead of being weighted twice — the sheet's `SUMPRODUCT(measures × block %) / total` counts "Refrão 45–82" and the solo measures inside it separately, and a 100-measure song cannot exceed 100%. Measures no log covers contribute 0, and so does a measure with no target row.
* **One song, many logs per day (2026-11-03):** the one-record-per-day rule recorded above applies to practice sessions and does not extend here. A song is practiced section by section — Intro once, Chorus twice, Solo on its own — so `song_progress_logs` holds several rows per day per song, and the log form writes a new row every save rather than editing the day's row (`src/components/SongView.tsx`). Editing and deleting stay per row, the way `SessionView` handles past records. Deliberate, decided 2026-11-03; the schema carries no per-day guard.
* **How a song's structure arrives (2026-11-03):** requirement 2's `Tab URL` becomes `songsterr_url` plus the identifiers a re-import needs (`songsterr_song_id`, `songsterr_revision_id`, `songsterr_image`), and the structure itself is filled by `scripts/import-songsterr.mjs` (`npm run import:songsterr -- <url or songId> [--part N] [--bpm N] [--update] [--dry-run]`) rather than typed measure by measure. Songsterr has no official API and `songsterr.com` sends no CORS header, so the fetch cannot run in the browser; the script reads the tab page's `<script id="state">` for songId/revisionId/image and the track list, then the CDN's per-track JSON. Tempo comes from that JSON's `automations.tempo` — the page state's own `tempo` field is the player's metronome default (72 BPM on every tab) and is never used — and both tempo and time signature carry forward from each marker to the next, Guitar Pro semantics, so Back In Black lands 100 measures at 94 BPM 4/4. A tab that states no tempo is refused rather than imported at the default; `--bpm N` sets one for every measure. Deliberate, decided 2026-11-03 (D5): `song_measure_targets` also accepts manual edits, so a hand-typed structure is possible. The import is idempotent by Songsterr's songId — an existing song is refused unless `--update` is passed — and `--update` rewrites the target rows while keeping the logs; when the measure count changed against existing logs it asks for an explicit answer first, since the logs then point at different measures. `percent` is never in the payload: the target triggers recompute it. `src/lib/__tests__/songsterr-import.test.ts` greps the script for those rules.
* **What the song screen shows of the structure (2026-11-03):** the 100 target rows are shown as tempo runs, not as 100 rows — consecutive measures sharing a tempo merge into one line, so Back In Black reads `1–100 · 94 BPM` and Master of Puppets reads six lines. The time signature is stored per measure and not displayed, because decision D3 makes it irrelevant to the percent and a run of measures that never change signature would be noise; it shows up when a tab actually changes it (`tempoRuns()` in `src/lib/songProgress.ts`). Logged blocks carry their own percent, `bpm_clean / target.bpm` over the measures the block spans (`blockPercent()`), which is the sheet's `BPM Limpo (%)` column. Deliberate, decided 2026-11-03; `src/components/__tests__/song-view-source.test.ts` pins the run list and the per-block percent.
* **Song chart reuses the exercise chart (2026-11-03):** the song screen plots `percentHistory()` through the same `ProgressChart` in percent mode — Y fixed 0–100, no legend, no series palette, tooltip naming the day and the percent — instead of a second chart component. Deliberate, decided 2026-11-03; `src/components/__tests__/chart-source.test.ts` pins the percent branch, and the dashboard keeps its BPM chart unchanged.
* **Address per screen (2026-11-06):** requirements 3.1–3.3 name the screens but say nothing about the browser's address, and until now the address carried no information: `App.tsx` kept a `listView` string plus `selectedExercise`/`selectedSong` objects, so all six screens sat at `/` and a reload returned to the landing screen. The app now routes with `react-router-dom@^7.18.5` — the current release, peer `react >=18`, so the app's React 18.3.1 is unchanged — over one address per screen (`/`, `/exercises`, `/exercises/<id>`, `/songs`, `/songs/<id>`, `/settings`) under one frame, with no `App.tsx`. Three deliberate choices. A row's screen reads its row by the id in the address (`src/hooks/useExercise.ts`, `src/hooks/useSong.ts`: one `.eq('id', id).maybeSingle()` each) rather than receiving the row from whichever list was open, so a reload and a shared link answer; the back control navigates to the catalog's path rather than `history.back()`, because a pasted link leaves no previous entry while the button's label names the list; and an address off the six redirects to `/` with `replace`, since every address the app itself writes is one of them. A row id naming nothing visible — deleted, mistyped, or another account's and so hidden by the SELECT policy of `20261102150000_add_user_ownership.sql`, a non-UUID being refused by Postgres as `22P02` — is one card (`src/components/MissingRow.tsx`), because a read cannot tell the three apart. Nothing else moved: the gate still holds the route slot back until the session resolves, `Max BPM` / `Last BPM` / `percent` stay trigger-written and never client input, and the preferences stay in the browser's `localStorage`. Deliberate, decided 2026-11-06; `src/__tests__/routes-source.test.ts` pins the route table, the parameter names, which tabs match by prefix, and the frame being the only holder of the browser-backed state. One consequence for whoever deploys: `BrowserRouter` needs a host that answers unknown paths with `index.html` — `npm run dev` and `npm run preview` already do, and CI deploys nothing, so no such rule lives in this repository.
